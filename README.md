# Wayback 文字化けフィックス

Wayback Machine に残る昔の日本語ページの文字化けを自動で直す Firefox / Chrome 拡張。

```
  拡張あり → 天国に一番近い男
```

URL を書き換える必要も、設定も、アカウントも要らない。web.archive.org を
いつもどおり開くだけ。

## 何が起きているのか

文字化けの原因は Wayback の保存ミスではなく、**charset 情報がどこにも無い**こと。

```console
$ curl -sD- https://web.archive.org/web/20001212075700/http://www.tbs.co.jp/tengoku/index-j2.html
content-type: text/html                  # charset が無い
x-archive-orig-server: Apache/1.3.14 (Unix)
x-archive-guessed-charset: shift_jis     # Wayback は判っているのに Content-Type に載せない
```

1. **HTTP ヘッダに charset が無い** — Wayback は `text/html` としか返さない。
2. **HTML 側にも宣言が無い** — 2000 年当時はブラウザが自動判別したので書かない慣習だった。
3. **現代のブラウザは自動判別をやめた** — ロケール既定 (多くは windows-1252) で
   解釈するため、Shift_JIS のバイト列が化ける。

バイト列自体は無傷なので、**正しい charset を宣言してやるだけで読める**。

## 仕組み

```
document_start ─▶ 同じ URL を再取得 (force-cache) ─▶ 文字コード判定
                                                          │
              ブラウザに表示 ◀── document.write ◀── デコード ┘
```

1. `document_start` で表示を一旦隠す (化けた状態のちらつきを防ぐ)
2. **同じ URL をもう一度 `fetch` して生バイト列を得る**
3. `src/detect.js` で文字コードを判定
4. UTF-8 でなく、かつブラウザの解釈と違っていれば、デコードし直して
   `document.write` で文書を差し替える

### なぜ再取得するのか

ブラウザは charset の無い応答をロケール既定で解釈済みで、その時点で壊れた
文字は U+FFFD に潰れている。DOM から元のバイト列は復元できないので、
取り直すしかない。

`cache: 'force-cache'` を付けているので、**通常は HTTP キャッシュから返り、
web.archive.org へのリクエストは発生しない**。Internet Archive は非営利の
アーカイブで、そこへ余計な負荷を掛けないことをこの拡張の設計条件にしている。

### なぜレスポンスを書き換えないのか

Chrome の Manifest V3 にはレスポンスボディを書き換える手段が無い
(`webRequest.filterResponseData` は Firefox 専用)。手動でエンコーディングを
切り替える既存の拡張が Chrome の更新で壊れてきたのはこのためで、
再取得方式なら通常の `fetch` と DOM 操作だけで完結する。

### なぜ `id_` を使わないのか

拡張は web.archive.org 上で動くので、Wayback が埋め込んだリンク書き換えと
ツールバーをそのまま活かせる。修飾子なしのパスなら
`x-archive-guessed-charset` ヘッダも付いてくるので、判定材料もむしろ増える。

### 触らないもの

- UTF-8 として妥当なフレーム (Wayback のツールバーや wrapper)
  - 例外は ISO-2022-JP。全バイトが 7bit なので UTF-8 としても妥当になる
- ブラウザが既に正しく解釈できているページ (`document.characterSet` と一致)
- 判定できなかったページ (当てずっぽうで差し替えない)
- HTML 以外の文書

ステータスコードでは選り分けない。Wayback は当時のステータスをそのまま再生する
ので、保存されているのが 404 や 500 のページということがある。ブラウザがその
本文を描画する以上、直す対象に含める。

## 判定ロジック

`src/detect.js` は上から順に試し、**必ず実際にデコードして日本語として自然かを
検証**してから採用する。当時のページは平気で嘘の charset を書くため、宣言が
あっても鵜呑みにはできない。

1. ポップアップからの手動指定
2. `ESC $` を含む → ISO-2022-JP (エスケープシーケンスで一意に決まる)。
   Wayback のツールバーが先頭に挟まるので、探索は文書全体に対して行う
3. UTF-8 として妥当 → そのまま (純 ASCII もここ)
4. `<meta charset>` / `<meta http-equiv>` / `@charset` の宣言
5. `x-archive-guessed-charset` ヘッダ
6. Shift_JIS / EUC-JP / ISO-2022-JP を総当たりし、統計スコアが最良で、
   かつ実際にかなが出現するもの
7. 判定不能。**何もしない**

スコアはひらがな・カタカナ・和文約物・漢字を加点、私用領域・半角カナ・
デコード不能バイトを減点し、非 ASCII 文字数で正規化した値。誤ったコーデックで
読むと私用領域や記号が並ぶので、これで十分に分かれる。

4 と 5 のラベルは `TextDecoder` が WHATWG のラベル表を実装しているので、当時
よく使われた `x-sjis` / `ms_kanji` / `windows-31j` / `x-euc-jp` といった表記
揺れはそのまま通る。

判定が外れたときはツールバーのアイコンからポップアップを開いて手動指定できる。

### 変換の ON/OFF

ポップアップのトグルで、そのページの変換を切れる。OFF はブラウザ本来の解釈
(= 化けた状態) の再現で、保持している生バイト列を差し替え前の `characterSet` で
読み直しているだけなので、**再取得も再読み込みも起きない**。直前と直後を見比べ
たいとき用。

タブ単位・その場限りで、設定としては保存しない。切り替えても表示が変わらない
ページ (「変換は不要でした」「直すところはありません」) ではトグル自体を出さない。

frameset のページでは複数のフレームが介入対象になるため、ポップアップは反転
ではなく**目的の状態**を全フレームへ送る。フレームごとに反転させると状態がずれる。

### かなの裏取りが要る理由

総当たり (6) の採用には、スコアに加えて**非 ASCII 文字のうち 5% 以上が
ひらがな・カタカナであること**を要求している。

スコアだけでは足りなかった。EUC-KR のバイト列を EUC-JP として読むと漢字が
並ぶため、漢字の加点だけでスコア 0.85 に達してしまう。実際に韓国語のページ
(naver 2003) が `euc-jp` と誤判定され、**正しく `euc-kr` を宣言してブラウザが
正常表示できていたページを、別の誤りに置き換えてしまっていた**。

当時の日本語ページでかなが 1 文字も無いものは実質存在せず、中国語・韓国語の
ページにかなはまず現れない。ここが最も強い判別材料になる。

宣言 (4) と Wayback のヒント (5) は出所がはっきりしているのでこの制約は
掛けない。中国語ページが charset を宣言していれば正しく直る。

## 開発

判定ロジックはもともと、同じ問題を解くために書いた Go のリバースプロキシから
移植したもの。判定順とスコアの重みはそちらと揃えてある (6 と 7 を除く)。

### 読み込む

**Firefox** — `about:debugging#/runtime/this-firefox` →「一時的なアドオンを
読み込む」→ `manifest.json` を選ぶ。

**Chrome** — `chrome://extensions` → デベロッパーモードを ON →
「パッケージ化されていない拡張機能を読み込む」→ このディレクトリを選ぶ。
`browser_specific_settings` について警告が出るが、Firefox 用の項目なので
無視して構わない。

### テスト

```console
$ node --test test/
```

判定ロジックはブラウザ API (`TextDecoder`) しか使わないので、Node からその
まま検証できる。テストのバイト列は `golang.org/x/text` のエンコーダで生成した
もの。

ブラウザでしか確かめられないこと (描画・フレーム・ちらつき・ポップアップの
疎通) は [`docs/manual-test.md`](docs/manual-test.md) に手順と、直すべき /
触ってはいけないページの一覧がある。

### 配布用の zip を作る

```console
$ ./package.sh
```

### スクリーンショットを作り直す

```console
$ node docs/store/build.js
```

ストア掲載文は [`docs/store/listing.md`](docs/store/listing.md)。

## 制限

- **`document.write` で文書を差し替える**ので、差し替え前に走ったページ内の
  JavaScript の状態は失われる。当時のページはほぼ静的なので実害は少ない。
- **中国語・韓国語ページは、宣言が無いと直せない。** 候補に `gbk` や `euc-kr` を
  足すだけでは駄目で、スコア関数が日本語向け (かなを加点し、ハングルは減点)
  なので言語ごとの評価関数が要る。安易に候補だけ増やすと、上に書いた韓国語の
  誤判定と同種の事故になる。
- 短い純 ASCII ページや日本語が数文字しかないページは統計スコアが効かない。
  手動指定が実質的な保険。
- iOS 版 Chrome には拡張機構が無いため使えない。iOS Safari は対応可能
  (未確認)。
